**Scope:** `apps/api/prisma/schema.prisma` (68 models, 21 enums) + `prisma.<model>.*` usage across `apps/api/src`.
**Mode:** READ-ONLY. No code or schema was modified. This is a code-usage audit (complements the row-count audit in `tasks/DB-AUDIT-2026-05-25.md`).

## 2. MISSING INDEXES

Prisma does **not** auto-create indexes on foreign-key columns for PostgreSQL (unlike MySQL). Every FK you filter or join on needs an explicit `@@index`. The following FK columns are queried but lack one:

| Model | Column | Where it's filtered | Severity | Why |
|-------|--------|--------------------|----------|-----|
| **`CleaningCycle`** | `equipmentGroupId` (`equipment_group_id`) | `equipment-groups/equipment-groups.service.ts:311` — `where: { equipmentGroupId: id, status: 'IN_PROGRESS' }` (the in-use guard run on every group edit/delete) | **Medium** | FK relation with **no `@@index`**. Existing indexes cover `[filterId,status]`, `[ahuId,status]`, `status` — none start with `equipmentGroupId`. Seq-scans `cleaning_cycles` on every equipment-group mutation. Recommend `@@index([equipmentGroupId, status])`. |
| **`FilterProfile`** | `cleaningProfileId` (`cleaning_profile_id`) | `cleaning-profiles/cleaning-profile.service.ts:235, 274, 301, 398` — `where: { cleaningProfileId: id }` on every profile version/delete + in-use count | **Low/Medium** | FK with no index (only `@@index([isActive])`). Correctness-grade more than perf today (`filter_profiles` ≈ 0 rows per prior audit), but it's the column the delete-guard `count()` runs on — index it before the table grows. Recommend `@@index([cleaningProfileId])`. |
| **`CleaningCycle`** | `profileId` (`profile_id`) | delete-guard count via `FilterCleaningProfile` lineage; cycles are looked up by profile during version operations | **Low** | Required column, FK relation declared optional, **no index**. Lower priority than the two above (most cycle reads go through `filterId`/`ahuId` composites) but the profile-side joins have no supporting index. Consider `@@index([profileId])`. |

**Already well-indexed (verified, no gap):** `audit_trail` (7 indexes incl. `[userId,timestamp]`, `chainPosition`), `notifications` (5 incl. `[forUserId,isRead,createdAt]`), `cleaning_cycles` (7 composites), `filter_events` (6), `pm_schedule_entries` (`[windowStart,windowEnd]`, `approvalStatus`, `scheduleId`), `replacement_schedule_entries` (`scheduleId`, `ahuId`, `[windowStart,windowEnd]`, `status`), `deviations` (`status`, `ahuId`, `createdAt`), `notification_logs` (`channel`, `status`, `recipient`, `createdAt`). The list-endpoint backing tables the brief called out are mostly covered.

> Verify the live DB matches schema before adding: prior audit F-10 found `_prisma_migrations` absent — migration state is filesystem-only, so the deployed indexes may differ from `schema.prisma`. Run `\d+ <table>` in psql before trusting the schema's index set.

## 3. MISSING FKs / onDelete — ORPHAN & DANGLE RISK

### 3a. Required column ↔ optional relation, NO `onDelete` (integrity guarded in code, not the DB) — NEEDS REVIEW

These are the highest-value findings in this section. The column is `String` (NOT NULL), but the Prisma relation is optional (`?`) with no `onDelete`, so the DB will not stop a parent delete from orphaning the child — and because the relation is optional, Prisma also won't enforce referential presence at the ORM layer.

| Model | Column / relation | Parent | Integrity actually enforced by |
|-------|------------------|--------|-------------------------------|
| **`CleaningCycle.profileId`** (required) ↔ `profile FilterCleaningProfile?` (optional, no `onDelete`) | `filter_cleaning_profiles` | **Service guard only.** Profiles are versioned via archive-and-insert (lineage), and `cleaning-profile.service.ts:398` does a pre-delete `count()` of bound `filterProfile` rows — but there is **no DB-level FK action** preventing a profile row delete from orphaning a cycle's `profileId`. By design cycles freeze `profileId`, so the archived row should persist; the safety net is the code guard, not a constraint. |
| **`FilterProfile.cleaningProfileId`** (required) ↔ `cleaningProfile FilterCleaningProfile?` (optional, no `onDelete`) | `filter_cleaning_profiles` | Same pattern — required column, optional relation, no `onDelete`. Integrity depends on the `cleaning-profile.service` in-use guard (`filterProfileCount` at :398), not a DB constraint. |

**Assessment:** acceptable *given* the service guards, but the guarantee lives in application code. A direct SQL `DELETE FROM filter_cleaning_profiles` (operator/script path) would orphan these required columns silently. If you want defense-in-depth, make the relation `onDelete: Restrict`.

### 3b. Relations declared WITH `onDelete: SetNull` that can null a column other code assumes present — NOTE

- `NotificationRuleRecipient.group` → `onDelete: SetNull` on `groupId`. Fine (recipient can fall back to role/user), low risk.
- (No other risky `SetNull` found — the `AssetInstance` parent self-relation was already hardened from `SetNull` to `Restrict`, per the schema comment at the `parent` relation, and `FilterDetails`/identifiers/etc. correctly cascade.)

### 3c. Soft-reference UUID columns (no Prisma relation) that can dangle

These store a UUID but declare **no** `@relation`, so the DB cannot cascade or restrict. Two buckets:

**(i) INTENTIONAL — documented "survives deletion" for 21 CFR audit durability. Do NOT add FKs.**
The schema explicitly comments these as soft-refs so the audit/ledger record outlives the referenced entity:
- `Deviation.{pmScheduleEntryId, ahuId, assignedUserId}` (comment: "Soft refs … so the deviation audit record survives schedule/entry deletion")
- `ReplacementScheduleEntry.ahuId`, `ReplacementExecution.{oldFilterId, newFilterId}` (comment: "AHU is a soft ref (no FK) to avoid coupling")
- `QualityNotification.{pmScheduleEntryId, scheduleId}` (comment: "Soft refs … so the audit record survives entry/schedule deletion")
- `BlockChangeRequest.{filterId, fromBlockId, toBlockId}` (request log — snapshots names alongside ids, deliberately decoupled)
- `AuditTrail.{userId, targetId, sessionId}` (audit trail is `VarChar`, intentionally not FK'd)

**(ii) UN-FK'd by convention (the data-ingestion `entityId` family) — these point at `AssetInstance.id`/`Filter.id` with no relation. Mostly benign because the ingestion feature is unused in prod, but they CAN dangle if an instance is deleted:**
- `DeviceCredential.entityId`, `LatestTelemetry.entityId`, `UnsMapping.entityId`, `ConnectivityStatus.entityId`, `DataStream.entityId`, `QrCode.entityId`
- `PmSchedule.entityId`, `PmScheduleEntry`→schedule (FK'd, ok), `PmExecution.entityId`
- `CleaningCycle.{filterId, ahuId, cleaningAreaId, pmExecutionId}` — `filterId`/`ahuId` point at typed `filters`/`ahus` (or `AssetInstance` pre-cutover) with no relation; `cleaningAreaId`/`pmExecutionId` likewise.
- `FilterEvent.{filterId, blockId, equipmentId, cleaningAreaId}` — only `cycleId` is a real relation; the rest are soft.
- `FilterDetails.assetInstanceId` IS FK'd (cascade); `currentCycleId`/`filterProfileId` ARE relations.

**Assessment for (ii):** VERIFIED — `instance.service.ts:567-577` deletes the entity instance's ingestion sidecars in one transaction (`deviceCredential`, `connectivityStatus`, `unsMapping`, `qrCode`, `latestTelemetry`, `dataStream`, plus `assetRelationship` + `assetIdentifier`, all by `entityId`/`assetId`). So the `entityId`-family soft refs are **manually cascaded** despite having no DB FK. Two caveats remain:
- The instance "delete" is actually a **soft delete** (`isActive: false` on the instances at :568) but a **hard delete** of those sidecars — asymmetric by design.
- The audit-retention soft refs (`cleaning_cycles.filterId/ahuId`, `filter_events.*`) are deliberately **left dangling** (21 CFR) — correct, but means querying cycles by a deleted filter's id still returns rows pointing at an inactive instance. Expected, just noting it.
The manual-cascade list is hand-maintained: if a NEW `entityId`-keyed table is added later and not added to this `$transaction`, it will silently orphan. Low risk today; flag for the next ingestion-table addition.

## 4. N+1 RISKS

| File:line | Model | Pattern | Severity |
|-----------|-------|---------|----------|
| **`modules/assets/helpers/descendant-collector.ts:6-17`** | `AssetInstance` | `collectDescendantIds()` — **recursive**, issues one `prisma.assetInstance.findMany` per node in the subtree (1 query per parent at every level). Called by `instance.service.ts:563` on entity delete. | **Medium.** Scales with tree size, not depth. Replace with a single recursive CTE (`$queryRaw WITH RECURSIVE`). Small hierarchy today (~4 blocks) caps the blast radius, but it's a genuine recursive N+1. |
| **`modules/uns/uns-path-builder.ts:153-171`** | `AssetInstance` | `getDescendantIds()` — BFS, one `findMany` per dequeued node. **Duplicate** of `collectDescendantIds` with the same N+1 shape. | **Medium.** Same fix (recursive CTE). Two near-identical descendant-walkers both N+1 — consolidate. |
| **`modules/uns/uns-path-builder.ts:45-64`** | `AssetInstance` | `buildUnsPath()` — ancestor walk, one `findUnique` per level up the parent chain. | **Low** (depth-bounded ~4 levels), called per entity on UNS recompute. |
| **`modules/filter-operations/filter-resolver.ts:272-278`** | `AssetInstance` | `BY_BLOCK` profile resolution walks Filter→AHU→Block one `findUnique` per level inside a `while` loop. | **Low** (depth-bounded), runs per cleaning-cycle profile resolution. |
| **`modules/notification-delivery/notification-dispatcher.ts:74-187`** | `NotificationRule`, `NotificationTemplate`, `Notification` | `for (const rule of rules)`: per-rule `resolveRecipients()` queries + per-rule template `findUnique` (×2) + nested `for (const user of users)` doing `prisma.notification.create` **one row at a time**. | **Medium** (bounded by rules×users). The in-app `notification.create` loop should be a single `createMany`. |
| **`modules/replacement-schedule/service.ts:225-239`** | `ReplacementScheduleEntry` | Upload commit loops `for (const c of toCreate) await tx.replacementScheduleEntry.create(...)` — one INSERT per row, up to 500 rows. | **Medium.** Use `tx.replacementScheduleEntry.createMany`. (Insert-side N+1, capped at 500 by the row-limit guard at :132.) |
| **`modules/assets/services/bulk-upload-filter.service.ts:215-234`** | `Filter` (via `filterService.create`) | `for (const c of toCreate) await filterService.create(...)` — each create is its own txn + RFID assignment. | **By-design / NEEDS REVIEW.** Each row needs full typed-create + identifier semantics, so `createMany` isn't a drop-in. Acceptable as-is but it is per-row work; flagged for visibility. |

**Verified NOT N+1 (well-batched):** `pm-schedules/pm-due-tasks.ts` (bulk fetch + Map joins, no in-loop queries), `hierarchy.service.ts:getTree` (single `include` tree + one `enrichFilterRows` batch).

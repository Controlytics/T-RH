## 1. Build pipeline — exact, ordered, from clean state

### 1a. Prerequisites (one-time, per build host)

| Requirement | Reference path on dev box |
|---|---|
| JDK 21 | `C:\Users\hello\jdk-21.0.2` |
| Android SDK | `C:\Users\hello\Android\Sdk` |
| `JAVA_HOME` env var | system-wide → JDK 21 path |
| `ANDROID_HOME` env var | system-wide → Android SDK path |
| Long-path support | registry: `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled = 1` |
| Node.js 20+ | for `vite build` and `cap copy` |
| `Reader_Usb.jar` in libs/ | `apps/android/android/app/libs/Reader_Usb.jar` (committed; verify present) |

`windowsIssues.md` §10 explicitly recommends building APKs on a dev desktop,
not the deployment server (Group Policy on AD-joined Windows Server can
disable long paths regardless of the registry; Capacitor's deep `node_modules`
paths exceed 260 chars without the long-path flag).

### 1b. Clean-state build commands (PowerShell, single shift)

Run from repo root in this exact order. Each command must succeed before
moving to the next.

```powershell
# 0. Verify env (one-time check per host)
$env:JAVA_HOME    # should print JDK 21 path
$env:ANDROID_HOME # should print Android SDK path
java -version     # should report 21.x
node --version    # should report v20.x or v22.x

# 1. Sanity check — confirm .env.production is the live build env file
Get-Content apps\web\.env.production
# Expected: VITE_API_URL=https://192.168.1.22:3000

# 2. Build the web bundle (this is what the APK ships)
cd apps\web
npx vite build
# Output: apps\web\dist\ (referenced by capacitor.config.ts -> webDir = ../web/dist)
cd ..\..

# 3. Mirror the dist into the Android project (Capacitor copies into
#    apps\android\android\app\src\main\assets\public\)
cd apps\android
npx cap copy android
cd ..\..

# 4. Build the APK
cd apps\android\android
.\gradlew.bat assembleDebug
cd ..\..\..

# 5. Locate the APK
# Output path:
#   apps\android\android\app\build\outputs\apk\debug\app-debug.apk
# Convention (per tasks\todo.md and PROJECT_ARCHITECTURE.md): rename a copy to:
#   DigiLog-FilterOps.apk  at repo root
Copy-Item apps\android\android\app\build\outputs\apk\debug\app-debug.apk `
          DigiLog-FilterOps.apk -Force
```

### 1c. When `gradlew clean` is required

A plain `assembleDebug` reuses the previous compile cache, which is fine
**unless** any of the following changed:

- `apps/android/android/app/build.gradle`,
  `apps/android/capacitor.config.ts`,
  `apps/android/package.json`, or any Capacitor plugin version
- The `Reader_Usb.jar` file in `apps/android/android/app/libs/`
- `RfidPlugin.java` or `MainActivity.java` (rare; confirms a real Java change)
- `network_security_config.xml` or `rootca.pem` under `res/raw/`
- After upgrading JDK or Android SDK on the build host

If any of those changed, prepend `.\gradlew.bat clean` before
`assembleDebug`. (Gradle daemon holds file locks; if `clean` fails with a
locked file, kill `java.exe` first via Task Manager and retry.)

### 1d. Tablet-side cache invalidation after install

The APK install replaces app code, but **does NOT** automatically clear:

1. **Service Worker cache** — The SW from the previous build is registered
   against the same origin (`capacitor://localhost`). Vite-plugin-pwa is set
   to `registerType: 'autoUpdate'` with `cleanupOutdatedCaches: true`, so
   the *next* navigation usually swaps caches and unregisters obsolete
   entries. But for a guaranteed clean state on a v3-IDB device that's now
   getting v5-IDB code, the operator should:
   - Settings → Apps → DigiLog → Storage → "Clear cache" (clears SW asset
     cache; does NOT touch IDB)
   - **Do NOT** "Clear data" — that wipes IDB too, which on a tablet with
     queued offline ops would silently drop unsynced work. Drain the queue
     first (verify "Data Synced" indicator green) before any "Clear data".

2. **IndexedDB (`digilog-offline`)** — schema migration v3→v4→v5 is
   idempotent and runs automatically on first `openDB()` call after the
   app boots. No manual intervention needed. The v3→v4 step backfills
   `tapeVersion = null` on legacy ops; v4→v5 adds 7 new sync stores
   without touching existing data. Confirm migration ran by checking that
   `syncVersionState` exists (DevTools → Application → IndexedDB on a
   USB-debug-attached tablet).

3. **JWT in sessionStorage** — wiped on app close (sessionStorage, not
   localStorage). Operator must log in once after the install regardless
   of whether they were logged in before.

**Recommended first-install sequence on each tablet:**
1. Drain offline queue on the existing build (operator confirms green
   "Data Synced" badge).
2. Install new APK (Settings → "Install unknown apps" allowed for the
   sideload source, e.g., file manager).
3. Open DigiLog → log in → tap "Filter Operations" once → close app.
4. Reopen → confirm IDB v5 stores present (or just verify a full cycle
   works; smoke-test 3 below covers it).

## 3. Risk flags — first install after Option D ships

### 3a. IDB v3 → v5 migration on existing tablets

- **Risk:** v3→v5 is technically a chained migration (v3→v4 backfills
  `tapeVersion`; v4→v5 adds stores). The handler iterates the migration
  blocks via `oldVersion < N` checks — verified idempotent in the source.
- **Concern:** If a tablet had unsynced ops in v2 IDB (pre-Phase 8.3),
  those rows lack `tapeVersion` entirely. The v3→v4 backfill writes
  `null` in place, and `null` skips the staleness check server-side. So
  pre-8.3 leftover ops will drain — but they're not protected from
  STALE_TAPE rejection. **Mitigation:** require operators to drain the
  queue on the previous APK before installing the new one. Audit the
  "Data Synced" indicator before each upgrade.
- **What can go wrong:** if the v3→v4 cursor walk throws (corrupt row),
  the upgrade transaction aborts and the IDB stays at v3. Symptom: app
  fails on first write because the code now requires v5 stores. **Fix
  path:** clear app cache + data (operator loses any unsynced ops) →
  fresh IDB at v5. **Pre-empt:** test the upgrade on a tablet with a
  representative dirty queue before fleet rollout.

### 3b. Service Worker cache shadowing the new build

- **Risk:** vite-plugin-pwa caches the previous bundle's `index.html`
  and JS chunks. With `registerType: 'autoUpdate'`, the new SW activates
  on the *next* navigation, but if the operator opens the app and
  immediately does a write, the *old* JS may run for one session.
- **Why this is dangerous for Option D:** the old JS expects v3/v4 IDB
  schema. If the upgrade has already silently bumped to v5 (because
  the new SW or app code touched IDB once during install), the old JS
  may reference stores that exist but don't have the data shape it
  expects.
- **Mitigation:** `cleanupOutdatedCaches: true` is set; pair with the
  manual "Clear cache" step in §1d before first launch. Alternatively,
  uninstall the old APK before installing the new one (loses queued
  ops — drain first).
- **Validation:** after install, on the tablet open
  `chrome://inspect` → Service Workers → confirm only one SW
  registration and its scriptURL points to the new build hash (the
  filename has a content hash baked in by Vite).

### 3c. HTTPS cert trust survival across APK upgrade

- **Question:** does the tablet's trust of `rootCA.pem` survive an APK
  reinstall?
- **Answer:** the `network_security_config.xml` declares trust via
  `<certificates src="@raw/rootca" />`, which means the cert is bundled
  inside the APK and re-installed every time the APK installs. So:
  trust is not stored on the tablet's user-cert store — it's part of the
  APK signature/resources. **APK upgrade preserves trust automatically.**
- **Edge case:** if a previous tablet had the cert manually installed
  via Settings → "Install certificates", that cert still lives in the
  user-cert store after an APK upgrade. No conflict — the system trusts
  both the bundled and the manually installed cert.
- **What can go wrong:** if the `rootca.pem` in `res/raw/` is rotated
  (mkcert root regenerated on the dev box), old tablets that were on
  the previous APK + had the previous cert in their user-cert store
  will start failing TLS once the API switches to the new cert. **Pre-
  empt:** keep `rootca.pem` stable; only rotate when forced; if rotated,
  notify the field that ALL tablets need the new APK simultaneously.

### 3d. Capacitor 8.x JDK requirement

- **Concern:** Capacitor 8.x requires JDK 17+; this repo uses JDK 21.
  Building with JDK 11 (older Android tooling default) will fail with
  obscure Gradle errors. Confirm `java -version` reports 21 before
  every build.

### 3e. APK signing for production sideload

- **Status:** the build commands above produce `app-debug.apk`, signed
  with the Android debug keystore (`~/.android/debug.keystore`,
  auto-generated). For internal cleanroom field use, debug-signed is
  acceptable; for any wider rollout, a release keystore should be
  configured (currently not in scope per `apps/web/CLAUDE.md`).

# DigiLog → Successor Platform — Rewrite Specification

**Date:** 2026-05-16
**Status:** Draft for stakeholder review (NOT an execution plan; requires product sign-off)
**Triggering ask:** complete removal of Entities, Entity Templates, Assets, Asset Templates, Alarms, Rule Chains from the codebase.
**Honest framing:** what this document specifies is **the discontinuation of DigiLog** and the bootstrap of a successor platform. The removal scope is not a refactor of DigiLog — it is the platform sunset described in `tasks/ENTITY-REMOVAL-IMPACT-ANALYSIS.md` plus two additional concept removals (Alarms, Rule Chains).

If the intent was something narrower than this, stop and re-scope. The waves below assume scorched-earth removal is what's wanted.

---

## 1. Scope statement

### 1.1 Concepts to remove

| Concept | DigiLog primary surface | Removes |
|---|---|---|
| Entities (`AssetInstance`) | Polymorphic asset model storing every filter, AHU, block, area, equipment | The data model that holds 100% of operator-facing physical objects |
| Entity Templates (`AssetTemplate`) | Type definitions + attribute schema + telemetry config + alarm rules + default rule-chain | The catalog of what kinds of things exist |
| Assets (synonym in this codebase for AssetInstance/AssetTemplate at the schema layer) | — | Same as above |
| Asset Templates (synonym) | — | Same as above |
| Alarms (`Alarm`) | Out-of-range telemetry detection + acknowledgment workflow + dashboard + history | The regulatory layer that makes this a 21 CFR Part 11 cleanroom logger |
| Rule Chains (`RuleChain` + 77 node types) | Data ingestion pipeline — every MQTT/HTTP message routes through it; alarms generated by analytics nodes, notifications dispatched by notification nodes | The platform's nervous system |

### 1.2 Downstream effects (forced by the removal)

These are not additional asks — they are **structural consequences** of removing the above. Each is listed because they cannot survive removal of their parent.

| Forced casualty | Reason |
|---|---|
| MQTT ingestion (`apps/api/src/transport/mqtt-handler.ts`) | Resolves topic → AssetInstance by `unsPath`; without AssetInstance there is no resolution target |
| HTTP telemetry ingestion (`apps/api/src/modules/data-ingestion/routes.ts`) | Resolves Bearer token → DeviceCredential → AssetInstance; same blocker |
| All telemetry storage (`ts_telemetry`, `ts_events`, etc.) | Hypertables partition on `entity_id`; without entities, the partition key is meaningless |
| Filter Operations (cycle start/advance/bypass/checklist) | Cycles are owned by a `filterId` (AssetInstance UUID) |
| Cleaning Cycles + Filter Events history | Same |
| PM Schedules + executions | Owned per AHU entity |
| Mobile / RFID scanner / offline sync | Every cached object is an entity |
| Reports | Entity-slot bound; historical PDF regen requires entity UUIDs to resolve |
| Dashboards | Every widget is entity- or telemetry- or alarm-scoped |
| UNS topic routing | `UnsMapping` is 1:1 with AssetInstance |
| Device credentials + Mosquitto dynsec ACL | Per-entity-bound; the broker loses authorization granularity |
| Block change request workflow | Inter-entity transfer of filters |
| Equipment Groups | Composite asset (block + 3 instruments) |
| Filter Cleaning Profiles + Filter Profiles + Checklist Profiles | All reference templates and entity instances |
| Audit chain coverage | ~70% of historical audit rows reference target_type ∈ {asset_instance, asset_template, alarm, rule_chain, filter, cycle, equipment_group, ...} → orphan-target on removal |

## 3. What gets added (PRODUCT DECISION REQUIRED)

This section is intentionally blank. The successor platform's purpose is not specified by removal alone.

**Open questions for the product owner:**

- What is the successor platform's primary function? It is currently scoped as "users + roles + audit + branding + notifications inbox" — that is a generic admin panel, not a vertical application.
- Is the goal to repurpose this codebase for a different vertical (which would benefit from removing the cleanroom-specific bits)? If so, what vertical?
- Or is the goal to deprecate DigiLog entirely and rebuild from scratch on a new stack? If so, what's the timeline + budget?
- Do the existing users + their roles + their audit history have to migrate?
- Does the cleanroom data (filters, cycles, alarms, telemetry) need to be preserved in read-only form for the 7-10 year 21 CFR Part 11 retention window?

**The waves below cannot start until these are answered.** Without an answer, "remove everything" produces a deployed login screen with no purpose.

## 4. Migration path (assuming scorched-earth removal is confirmed)

### 4.1 Pre-flight (mandatory, before any deletion)

| Step | Action | Required output |
|---|---|---|
| 1 | Full backup of `digilog_db` + `digilog_tsdb` to long-term archive (S3, network share, write-protected disk). Archive must be retained 7-10 years per 21 CFR Part 11. | Two `.dump` files, verified by `pg_restore --list` |
| 2 | Operator-facing freeze announcement: no new cleaning cycles, no new PM tasks, no new entity creation. | Communication artifact |
| 3 | Drain all `IN_PROGRESS` cycles → force-complete or terminate-with-reason. | All `CleaningCycle.status IN ('COMPLETED', 'TERMINATED')` |
| 4 | Generate final reports for every active entity + cycle + PM schedule. Sign with electronic signature. Archive. | PDFs with signature metadata in `report_instances` |
| 5 | Export TSDB to columnar archive (Parquet) for 21 CFR retention. | Parquet files keyed by `entity_id`, time range |
| 6 | Final audit-trail snapshot: `pg_dump` of `audit_trail` table specifically, signed by SUPER_ADMIN, retained separately. | Standalone dump file with manifest |
| 7 | Inspector / regulator notification (if applicable). Some jurisdictions require notification before retiring a 21 CFR-compliant system. | Regulatory documentation |

**Pre-flight is 1-2 weeks of calendar time minimum, regardless of how fast the code work is.**

### 4.2 Wave 1 — Backend ingestion stop (1 day)

Goal: stop new data from entering. After this wave, MQTT and HTTP ingestion return errors; nothing else is yet deleted.

- Disable `apps/api/src/transport/mqtt-handler.ts` subscription (don't connect to broker)
- Return 410 Gone from `/api/data/telemetry` and `/api/data/attributes`
- Stop graphile-worker ingestion job consumers
- Devices in the field begin queueing locally and erroring; this is expected and documented

**Rollback:** re-enable the disabled handlers; ingestion resumes. Reversible until Wave 2 starts.

## 5. Regulatory implications (21 CFR Part 11)

**Decisive question:** is the successor platform still claiming 21 CFR Part 11 compliance?

### 5.1 If YES (compliance retained)

The retained audit chain + electronic-signature columns + user/role/session machinery can support compliance claims for the surviving subsystems (user management, audit). **But:**

- The audit chain has orphan-target rows for ~70% of historical entries. The verifier can prove the chain itself wasn't tampered with, but the targets those rows point to no longer exist. An inspector may consider this an integrity compromise. Get inspector sign-off before deletion.
- The pre-flight backups must be retained in restorable form for the regulatory retention window (typically 7-10 years). They cannot be reduced to PDF.
- Any data subject inspection or eDiscovery request that arrives during the retention window must be servable by restoring the backup into a sandbox.

### 5.2 If NO (compliance dropped)

The successor platform is a different regulatory class. The DigiLog audit data still needs to be retained per the original compliance scope (because it WAS compliant when collected), but the new platform itself doesn't need the audit machinery. You could trim audit further or replace it.

**Important:** dropping compliance is itself a regulated action in some jurisdictions. Check with legal/regulatory before deciding.

### 5.3 Inspector / regulator notification

Some jurisdictions require advance notification when retiring a 21 CFR-compliant system. Verify before executing Wave 5.

## 7. After the rewrite: what is the platform?

If Section 3 (what gets added) remains empty, the result is:

- A login screen
- A user management UI
- A role + permissions admin
- An audit trail viewer (mostly empty / orphan-target rows)
- A notifications inbox (with nothing creating notifications)
- ~10 config pages for branding, LDAP, password policy, datetime format, backup, etc.
- An LDAP/AD integration
- A health dashboard
- A help-articles editor

**That is a generic admin panel.** It is functional but has no product. Operators have nothing to do on it once they're logged in.

**The rewrite spec is therefore incomplete until the product owner answers Section 3.** Without an answer, "complete the removal" produces a deployed admin panel with no purpose — which is technically successful execution but not a useful outcome.

## 8. Recommended decision

If the underlying ask is "the DigiLog brand / codebase will be retired and we're starting a new product", **don't do the destructive removal at all**. Archive the DigiLog repo, take final backups, and start the new product in a fresh repo with a fresh stack. Migration cost is roughly the same and you avoid the regulatory + git-history baggage.

If the underlying ask is "DigiLog has become too complex and we want a leaner version", **the right answer is to define what 'leaner' means** (Section 3) *before* deleting half the platform.

If the underlying ask is "we want to repurpose this codebase for a different vertical", **specify the new vertical first** so the surviving modules can be shaped toward it.

In all three cases the next step is **product input**, not code deletion.

## Appendix A — Cross-reference with strict audit (`tasks/STRICT-AUDIT-2026-05-16.md`)

The strict audit ran in parallel and surfaced **11 CRITICAL findings** on the application **as it is today**. They are independent of the removal scope and should be addressed regardless of which decision (rewrite vs. don't-rewrite) is taken.

**Removal-spec-relevant overlap:**

- The audit's CRITICAL findings around audit-chain integrity (§1.1–1.3, §1.6 of the audit) become **more dangerous**, not less, if removal happens. The orphan audit-trail rows (target_type ∈ {asset_instance, alarm, rule_chain, etc.}) compound with the existing chain-integrity gaps to make any 21 CFR Part 11 claim post-removal indefensible.
- The audit's CRITICAL backup findings (§1.9, §1.11) directly affect the pre-flight wave: streaming + password-hash stripping must be fixed BEFORE the backup is taken, or the archive contains corrupted/leaked data.
- The audit's CRITICAL idempotency finding (§1.10) is moot if cycles disappear — but until then, it should be fixed.
- The audit's perf findings (§1.7, §1.8) compound in the rewrite waves: a slow / DoS-prone API makes the Wave 1 ingestion-stop test difficult to validate.

**Recommendation order if BOTH the removal and the audit fixes are wanted:**

1. Fix audit-chain integrity CRITICALs first (§1.1, §1.2, §1.3, §1.6 of the audit) — required to make the eventual data archive provably intact.
2. Fix backup CRITICALs (§1.9, §1.11) — required to make the pre-flight archive itself defensible.
3. Take pre-flight backups (rewrite spec §4.1).
4. Execute the removal waves (rewrite spec §4.2–§4.7).
5. After removal, the rewrite's surviving codebase still has the auth-plugin / unbounded-list / WS-leak issues — fix those in the successor.

# DigiLog — Deep Database Audit (2026-05-25)

**Scope**: Production-grade audit of `digilog_db` (PostgreSQL 18, Prisma 6.3).
**Scoring axes**: severity (Critical / High / Medium / Low), data-integrity impact, runtime impact, compliance impact, migration complexity, rollback risk.
**Author**: This document, written from live `pg_stat_*` + `pg_constraint` + `information_schema` reads + Prisma + grep audit of the repo. Every claim cites either a query, a file path, or a numeric count taken at audit time.

---

## 0. Executive Summary

The database is **mid-architecture-migration**. The 2026-05-17 typed-hierarchy migration added 4 sidecar tables (`blocks`, `areas`, `ahus`, `filters`) intended to replace the single-table polymorphic hierarchy (`asset_instances`). **That migration was started but not finished** — `asset_instances` is still the FK target for `cleaning_cycles.filter_id`, `filter_events.filter_id`, `asset_identifiers.asset_id`, `filter_details.asset_instance_id`, and the parent-chain walker in `resolveFilterProfile`. The sidecars hold parallel data but are **not authoritative**.

## 2. Findings by category

### 2.1 CRITICAL (4)

**F-01 — `asset_instances` still authoritative**

| | |
|---|---|
| Table/column | `asset_instances` (entire table) |
| Why | The 2026-05-17 typed-hierarchy migration added `blocks/areas/ahus/filters` sidecars but did not migrate the FK references. `cleaning_cycles.filter_id → asset_instances(id)`. `filter_events.filter_id → asset_instances(id)`. `asset_identifiers.asset_id → asset_instances(id)`. Dropping `asset_instances` deletes every filter, block, AHU, area in the system. |
| Runtime impact | Universal — every API touching the hierarchy fails. |
| Frontend impact | Filter list, hierarchy diagram, cycle history — all break. |
| Compliance | Audit chain breakage (filter_events FK violations). Inspector blocker. |
| Fix | Multi-week migration: cutover all FKs from `asset_instances` to `filters/blocks/areas/ahus`. NOT a single-session task. |
| Rollback | Trivial — don't ship anything; data unchanged. |

**F-03 — Dual FK targets cause silent drift**

`filters` and `asset_instances` both hold filter rows. There is no enforced sync. A row inserted into `asset_instances` directly (e.g., via SQL or a script that bypasses the FE) won't appear in `filters`. The reverse can also happen. Both code paths read different tables:
- `cleaning_cycles.filter_id` resolution uses `asset_instances`
- The 2026-05-17 `filters` sidecar is intended for typed queries but most reads still use `asset_instances`

| Fix | Either complete the cutover (drop the legacy code paths) or add a check constraint enforcing 1:1 sync. |

**F-05 — Reauth password leak in `system_config`**

✅ **Already fixed today** (commit `204316e`). `_currentPassword` field was being persisted into `config_value` JSONB. Fixed by stripping underscore-prefixed keys in `configService.updateConfig` before save.

**Compliance/security note**: any prior backups of the DB taken between approximately the day someone first PUT a reauth-gated config and today contain plaintext passwords. Audit your backup retention.

**F-10 — `_prisma_migrations` table missing**

Prisma tracks applied migrations by writing to `_prisma_migrations` in the target DB. The table doesn't exist here. Either:
- Migrations were applied via `prisma db push` (no history tracked), or
- The table was dropped at some point.

**Impact**: a fresh `prisma migrate deploy` against this DB will try to re-apply all 16 migrations. Several will fail because their changes are already present (e.g., `add_typed_hierarchy_tables` would conflict).

| Fix | Either: (a) manually create `_prisma_migrations` and seed it with the 16 applied migration entries, OR (b) accept that disaster-recovery requires manual schema repair + selective migration replay. |

### 2.2 HIGH (5)

**F-02 — 26 empty tables clutter the schema**

Already enumerated in §1.5. None can be dropped without verifying they're not referenced by code/seed/migration. Recommended grep audit:

```bash
for table in dashboards dashboard_widgets dashboard_assignments \
             connectivity_status latest_telemetry dead_letter_queue \
             qr_codes entity_assignments template_assignments \
             user_group_members notification_logs notification_rule_recipients; do
  count=$(grep -rE "\b${table}\b|\b$(echo $table | sed 's/_\([a-z]\)/\U\1/g')\b" apps/ packages/ --include="*.ts" --include="*.tsx" --exclude-dir=node_modules | wc -l)
  echo "$table → $count code references"
done
```

Each with 0 references → safe DROP. Each with > 0 needs case-by-case review (refs might be re-exports, type imports, etc.).

**F-04 — 30+ never-used indexes**

The sidecar tables (`blocks`, `areas`, `ahus`, `filters`) have 4-5 indexes each created on creation, all with `idx_scan = 0` because the readers still use `asset_instances`. Total wasted disk: ~640 KB (negligible) but each index slows down INSERTs.

| Fix | Drop indexes with idx_scan = 0 AND > 7 days old. Re-create when sidecar reads come online. |

**F-26 — `password_history.password_hash` has no index**

Currently every password change scans all 95 rows. At 1000 users × 12 history rows each → 12,000-row scan per change. Cheap now, slow later.

| Fix | `CREATE INDEX password_history_user_id_password_hash_idx ON password_history(user_id, password_hash)` — composite, supports the bcrypt-compare loop. |

**F-15 — Notification dispatch broken or unused**

`notification_logs` (0 rows) + `notification_rules` (1 row, seed) + `notification_rule_recipients` (0 rows). The dispatch code (`apps/api/src/modules/notification-delivery/`) exists. Either nobody set up notification rules or the dispatch fails silently. Investigate before relying on email/SMS for production.

**F-22 — Reports never generated**

`report_templates` (2) + `report_template_versions` (24) but `report_instances` (0). Either the report-generation job isn't being run or it always fails. Investigate before assuming PDFs are being produced.

### 2.3 MEDIUM (10)

**F-06 — `terminate-cycle.ts` writes `completedAt`, not `terminated_at`**

```ts
// apps/api/src/modules/filter-operations/cycle-write/terminate-cycle.ts:74
data: { status: 'TERMINATED', completedAt: new Date() },
```

Should also set `terminated_at = new Date()`. Direct SQL termination today set both. Inconsistency: cycles terminated via the app show `completed_at = X, terminated_at = NULL`; cycles I terminated via SQL today show both. Confusing for auditors.

| Fix | One-line change: add `terminatedAt: new Date()` to the update. Backfill historic TERMINATED rows: `UPDATE cleaning_cycles SET terminated_at = COALESCE(terminated_at, completed_at) WHERE status = 'TERMINATED' AND terminated_at IS NULL`. |

**F-11 — `device_credentials.access_token` plaintext + indexed**

The `device_credentials_access_token_key` (16 KB UNIQUE) suggests tokens are looked up directly. Table is empty so no real exposure, but the design stores access_token in plaintext. If device-ingest ships, tokens should be hashed-at-rest.

**F-25 — MT-removal residue**

10 tables/columns from multi-tenancy are still in the schema. None hold data anymore. Drop in a coordinated wave; verify each isn't referenced by enum types or remaining `organization_id`-style columns.

**F-27 — `audit_trail.session_id_idx` unused**

Index size 120 KB, scans = 0. Auditors don't filter by session. Safe to drop.

**F-28 — `sessions.token_hash_key` unused**

144 KB UNIQUE INDEX. Sessions are looked up by `id` (UUID PK), not by `token_hash`. The UNIQUE column should stay (uniqueness constraint), but the redundant index can be dropped if there's no lookup pattern. Verify: `grep -rE "token_hash|tokenHash" apps/api/src/` first.

**F-29 — Two config tables**

`system_config` (30 rows) + `ingestion_system_config` (33 rows). The split is historical. Consolidate to one (`system_config`) in a future refactor.

**F-30 — `field_id_config.field_id_key` unused**

UNIQUE INDEX, 0 scans. Either the readers use a different column or never look it up. Investigate.

**F-09 — Help article versions growing 2:1**

`help_articles` (164) × `help_article_versions` (327) = roughly 2 versions per article. Snapshot-on-update is by design but unbounded growth. Add a retention policy (e.g., keep last 10 versions per article).

**F-17 — `electronic_signatures` empty**

Either signature feature isn't being used or it isn't wired. If keeping, fine. If not shipping, drop.

**F-18 — PM never fires**

`pm_executions` empty despite 8 schedules + 53 entries. Either the PM cron isn't running (`packages/queue/`) or PM-eligible filters never reach the trigger window. Check `worker.ts` + scheduler logs.

### 2.4 LOW (11)

F-07 (cycle code numbering off), F-12 / F-13 / F-14 (empty residue tables — already listed), F-16 (filter_profiles dead), F-19 (data streams), F-20 (template_kinds barely used), F-21 (UNS unused), F-23 (checklist_reviews unused), F-24 (admin_requests low usage), F-08 (compliance doc, not a bug).

Each is a small individual cleanup; together they remove ~30% of the schema's tables but require ~1 day of focused grep-audit + sign-off.

## 8. Single-page summary for non-technical readers

The database is in working condition but has accumulated migration debt and unused feature tables. Critically:

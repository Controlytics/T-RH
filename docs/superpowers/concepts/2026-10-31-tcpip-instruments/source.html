The answer in short

The application does the reading itself. A small part of the application — the TCP/IP Reader — connects to each TCP/IP instrument's IP address and port, reads its registers every 60 seconds, and turns them into that instrument's own keys. The desktop program in TCPIP/ is no longer needed.

Each instrument holds its own IP address, port and register map — so instruments in one profile can carry different keys. The profile holds only how they are read (every 60 s, unit ID 1) and which key names are judged. Every reading then enters the same path MQTT, HTTP and gateway readings use today, so offsets, limits, alarms, history, dashboards, reports and the audit trail work without any change.

Gateway profiles do not change at all.

What changes

1
One new choice when a profile is created. Gateway is selected by default, so nothing changes for anyone who ignores it.
2
Every profile card shows its connection — so a list of profiles tells you at a glance which ones are read by the application.
3
The profile holds only how its instruments are read — every 60 s, unit ID 1. It has no keys of its own: each instrument gets its own register map (next page).
Why "TCP/IP (Modbus)" and not just "TCP/IP"? The application already accepts devices that push over raw TCP (a Gateway-type connection). The word Modbus keeps the two apart.
Can it be changed later? Only while the profile has no instruments — afterwards the two kinds of instrument hold different settings.
Existing profiles (T&RH Sensors, iot) become Gateway automatically. No data moves.

What changes

1
Its own IP address and port. Shown only when the chosen profile is TCP/IP; port 502 is filled in. "Is Gateway" and "Reports through gateway" are not offered.
2
Its own register map. Instruments in one profile can carry different keys — 101-01 sends six; the next device may send only Temperature and Pressure.
Identical devices are not typed twice. Copy from instrument… takes another instrument's map; Import keys file reads today's ModbusTCPReader_keys.json.
Judged as still comes from the profile's Measurements: a key named Temperature or Humidity (device keys temperature, t · humidity, h) gets limits and alarms; every other key is shown, never judged.
Checked before saving: two keys in one register, a FLOAT32 running past the map, more than 125 registers in one read. The server refuses the same.
The cost of keys per instrument: when a device model changes, each of its instruments is edited — quick with Copy from instrument, and every change is in the audit trail.

Rules

What the feature promises — and what stays exactly as it is

TCP/IP Instruments
Draft 31-10-2026

SAME Stays exactly as it is

  • Gateway profiles and instruments — MQTT, HTTP, WebSocket, raw TCP, gateways, tokens, device certificates
  • Limits, offsets, decimals — set per instrument, as today
  • All five alarm sources — limits, inactivity, RS485, sensor range, offline
  • Dashboard, built dashboards, trend page, Data Report, Alarms, Settings
  • Report review, downloads and signatures
  • Audit trail — and every new setting is recorded in it

NEW How TCP/IP instruments behave

  • Each instrument has its own register map — keys can differ between instruments in one profile
  • Read-only. The application never writes to a device — writing to plant equipment from a 21 CFR Part 11 system is a separate decision
  • One path: every reading enters the same ingest as MQTT readings — no second way into the database
  • Each instrument has its own IP and port — no two instruments share one
  • Every 60 s by default, per profile, never faster than 10 s
  • A reading's time is the moment it was read
  • A failed read stores nothing — never a zero, never a repeat of the last value
  • Disabled instrument = not read

21 CFR Part 11 and validation

  • Register map, connection and address changes need remarks and a signature, like every instrument change today
  • Each change is an audit record with the old and new value
  • Test connection reads only and is not stored — it cannot create a reading
  • The Reader's own events (started, device not answering, recovered) are logged with times, so an outage can be explained later
  • OQ test cases to add: register map, test connection, a failed device, an address clash, a disabled instrument
How it would be delivered— each part tested and usable on its own
Part 1Profile, instrument address and keys

The Gateway / TCP/IP choice, IP, port and register map on each instrument (Copy from instrument, Import keys file), Test connection, the audit records. Nothing is read automatically yet.

Part 2The Reader inside the server (option A)

Reads every enabled TCP/IP instrument on its profile's schedule, through the same ingest; the connection card on the instrument page; device-not-answering records.

Part 3Plant Reader for AWS (option B)

The Windows service, the Plant Readers page and keys, keeping readings through an internet outage; bulk-upload columns; OQ test scripts for all of it.

Today's 101-01 and the desktop tool
Create the TCP/IP profile→Move 101-01 to it: enter 192.168.1.24 : 502, import the keys file→Test connection → readings arrive from the application→Close the desktop tool→Withdraw the old 101-01 token

Your decisions

Five answers, then I write the design and build it

TCP/IP Instruments
Draft 31-10-2026
1

Where will the Reader run?

A — inside the server at the plant · B — a Plant Reader on a plant PC, server in AWS · or both. This decides whether page 8 is built.

RecommendedBuild once, offer both. Start with the one Granules' production uses (still an open point in the DS document).
2

What is the option called on screen?

"TCP/IP" alone could be confused with the raw-TCP push devices already use.

Recommended"TCP/IP (Modbus)".
3

How often is a device read?

The desktop tool reads every 200 ms — 2.6 million rows a day for one instrument. The plant reports per minute today.

Recommended60 seconds by default, set per profile, never under 10 seconds.
4

Should the application ever write to a device?

The desktop tool can write registers and coils. In a validated system that is a control action, not monitoring.

RecommendedNo — read-only. Writing would be its own project with its own validation.
5

101-01 and the desktop tool

101-01 is fed today by the desktop tool over unencrypted MQTT, and its token sits in a plain file.

RecommendedMove 101-01 to the new profile, retire the tool, withdraw the old token (page 9).

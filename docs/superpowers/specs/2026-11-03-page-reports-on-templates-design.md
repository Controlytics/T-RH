# Page reports on templates — design (2026-11-03)

Operator, after the widget-reports deploy and a list of what "reports" still lacked: **"go ahead with page reports on templates"** (standing rule: "go ahead" = spec → plan → build, no pausing). This follows `docs/superpowers/specs/2026-11-02-widget-report-templates-design.md` (the widget build) and closes its non-goal "editing the built-in Data Report / Alarm Report / Trend PDFs … a later pass can move them onto templates" and its ruling T3-1 (page reports still write snapshot v2).

## 1. The ask

The five built-in PDF reports the pages produce — Data Report, Instrument Trend, Instrument Alarms, Alarm Report, Audit Trail — must be drivable by the SAME report-template model a dashboard widget's download uses: header (title, subtitle, company, app name, logo, accent), information rows, columns (which, heading, order, unit), footer (text, page numbers, printed by / at, signature line), page (orientation, typography), notes (remarks label, legend) — administered on Configuration → Report Templates, per instrument profile where the report is about instruments, and frozen in the report's snapshot so an approved copy cannot change under its signatures.

## 2. What exists today (recon 2026-11-03 at `ea7dee92`, the AWS tip)

- `REPORT_KINDS` (`packages/shared/src/types/report-downloads.ts`) = 8 page kinds + 14 widget kinds. The 8 page kinds are produced by FIVE builders: **Data Report** (`data-report`, `time-series`, `trend-header` — one document, `renderDataReports`, `apps/web/src/routes/instruments/trend-report.ts:347`), **Instrument Trend** (`temperature-trend`, `humidity-trend` — `renderTrendReport` :200, chart image only, no table), **Instrument Alarms** (`instrument-alarms` — `renderAlarmsReport` :415), **Alarm Report** (`alarms` — `routes/alarms/alarms-report.ts:429` + an inline `createReport` in `routes/alarms/index.tsx:233`), **Audit Trail** (`audit-trail` — inline in `routes/audit/index.tsx:391`).

- `ReportDownloadDialog` has the `extra` slot (template lines + a per-profile picker) that only the widget dialog uses.

## 3. Goals, non-goals, anti-goals

**Goals.** G1 Every page report kind has a template kind on Configuration → Report Templates, edited with the SAME editor and live preview as a widget kind. G2 A page report drawn with no template looks EXACTLY as today (title, info rows, columns, legend, typography, orientation, limits-hide rule, level columns) — the built-in template IS today's layout. G3 A page report drawn from a template prints that template's chrome, info rows and columns. G4 Every page report now writes snapshot **v3**: the chrome is frozen whether a template or the built-in drew it; replay fetches nothing. G5 One template model, one table, one API, one editor — no second system.

**Non-goals (this build).** `key:<telemetry key>` columns on page reports (the Data Report keeps its temperature and humidity columns; the profile's extra keys on the Data Report / Trend PDF remain the widget-data-keys phase-4 follow-up). Templates per dashboard or per user. Freezing Printed Date & Time (today it is the replay instant on every version; unchanged, noted). Excel exports. The trend chart's drawing (it stays the page's PNG). Scheduled / e-mailed reports.

**Anti-goals.** A figure printed differently from the page (cells stay the page's formatted strings; a template's `decimals` never re-rounds a formatted value — the widget rule C1 holds). A report that silently drops a column (a column the kind cannot fill prints empty cells and ONE "Not available" line, as widgets do). A replay that reads today's Branding into yesterday's approved report. A built-in that drifts from today's output.

## 4. Vocabulary

- **Template kind** (`TemplateKind`) — what a template is FOR: a widget type (`WIDGET_TYPES`, 14) or a **page template kind** (`PAGE_TEMPLATE_KINDS`, 5): `page:data-report`, `page:trend`, `page:instrument-alarms`, `page:alarms`, `page:audit-trail`. Stored in the `kind` column (today `widget_type`). Validated strings, no enum.
- **Download kind → template kind** (`templateKindOf(downloadKind)`): `data-report` / `time-series` / `trend-header` → `page:data-report`; `temperature-trend` / `humidity-trend` → `page:trend`; `instrument-alarms` → `page:instrument-alarms`; `alarms` → `page:alarms`; `audit-trail` → `page:audit-trail`; `widget:<t>` → `<t>`. Report Settings (Direct / Request per download kind), approvers, audit `reportType` and `reportTypeMatchesKind` are UNCHANGED — the download kinds stay what they are; only the template lookup maps them.
- **Scope of a kind** (`TEMPLATE_KIND_SPECS[kind].scope`): `'profile'` (a template belongs to one instrument profile — every widget type, `page:data-report`, `page:trend`, `page:instrument-alarms`) or `'application'` (one set of templates for the whole application, `profile_id` NULL — `page:alarms`, `page:audit-trail`, whose rows carry no profile).
- **Profile fields** (`TEMPLATE_KIND_SPECS[kind].profileFields`): `'all'` (key: and attr: — the reportable widget types as today, via `widgetTypeTakesProfileFields`), `'attributes'` (`attr:` only — the three per-profile page kinds), `'none'` (pie chart, alarm counts, text card, floor plan, the two application kinds).
- **Chrome** — header, logo, footer, page, notes; frozen in the snapshot (`ReportChrome`, v3).

## 5. Data model — `report_templates` (40 models unchanged; ONE migration)

Migration `20261103120000_report_templates_page_kinds`, hand-authored, both DBs:

1. `ALTER TABLE report_templates RENAME COLUMN widget_type TO kind;` — Prisma field `kind String @map("kind")`. The wire field, the query parameter, the audit `afterValue` key and the editor's URL parameter are renamed `kind` with it (one vocabulary; yesterday's audit rows keep `widgetType` in their stored values — history, not read back).
2. `ALTER TABLE report_templates ALTER COLUMN profile_id DROP NOT NULL;` — NULL = application-wide. The FK stays (CASCADE on a profile's delete; NULL rows are untouched).
3. Drop the three unique indexes and recreate them NULL-safe, because Postgres treats NULLs as distinct: `report_templates_scope_kind_name_key` on `(COALESCE(profile_id, ''), kind, name)`, `report_templates_scope_kind_lower_name_key` on `(COALESCE(profile_id, ''), kind, lower(name))`, `report_templates_one_default` on `(COALESCE(profile_id, ''), kind) WHERE is_default`. The `@@unique([profileId, widgetType, name])` line leaves `schema.prisma` (Prisma cannot express COALESCE; the hand index IS the rule — the routes keep answering its P2002 as 409 `TEMPLATE_NAME_IN_USE`). The migration guard test (`lib/__tests__/migration-guard.test.ts`) and `db:verify-migrations` must stay green; `prisma migrate diff` noise is stripped as on every migration here.
4. A CHECK: `(kind LIKE 'page:%' AND kind IN ('page:alarms','page:audit-trail')) = (profile_id IS NULL)` is NOT added — the API enforces scope (400 `SCOPE_MISMATCH`: a profile id on an application kind, no profile id on a profile kind); a database CHECK would have to repeat the kind list. The service re-checks on every write.

## 7. API (`apps/api/src/modules/report-templates`; 27 modules unchanged, no new route)

- Every route speaks `kind` (query / body / row). `GET /?profileId&kind`: `profileId=` omitted lists every row; for an application kind the rows have `profileId: null`.
- `GET /catalogue?kind&profileId?`: `profileId` REQUIRED for a profile-scoped kind (404 `PROFILE_NOT_FOUND` as today), REFUSED (400 `SCOPE_MISMATCH`) for an application kind. Fields = the kind's built-ins, then by `profileFields`: `'all'` → key: + attr: (today's rule), `'attributes'` → attr: only (sensor-offset keys SUPER_ADMIN-only, as today), `'none'` → built-ins only.
- `GET /resolve?kind&instrumentIds?`: a profile kind resolves as today (sections per profile, visibility-scoped, ≤ 200 ids, `REPORT_TEMPLATE_RESOLVE_IDS_MAX`); an application kind takes NO ids (400 `SCOPE_MISMATCH` if sent) and answers ONE section `{ profileId: null, profileName: null, instrumentIds: [], template: <the kind's default> | null }`.
- `POST` / `PUT /:id` / `PUT /:id/default` / `DELETE /:id`: unchanged gates (SUPER_ADMIN by role, re-auth `UPDATE_REPORT_TEMPLATE`, audit `REPORT_TEMPLATE_*` with the document; the audit `afterValue` carries `kind` and `profileId: null` for an application template, `profileName: null`). "Set as default" clears the other default **of the same scope** (NULL profile = the application scope) in one transaction; the profile row lock is skipped for the application scope and replaced by `pg_advisory_xact_lock(hashtext('report_templates:' || kind))` so two concurrent set-defaults cannot both win (the partial index is still the invariant).
- Instrument list route: `profileId` already declared; the Data Report page's client type gains it (web).

## 8. Which template a report uses, and what the built-in does

- **Profile kinds** (Data Report, Trend, Instrument Alarms): the page sends `GET /resolve?kind=page:…&instrumentIds=…` with the instruments it will print; each instrument's SECTION uses its profile's default (its columns and info rows), the CHROME is the first printed instrument's template (the widget rule R4, so a three-profile Data Report has one header). No template for a profile = that section prints the built-in layout.
- **Application kinds** (Alarm Report, Audit Trail): `GET /resolve?kind=page:alarms` → the one default or null.
- **Built-in** = `builtinReportTemplate(kind)` drawn through the SAME templated path — with two exceptions kept inside the Alarm Report's row builder so G2 holds: when NO saved template is in use, the INSTRUMENT ID / AREA / LOCATION columns follow the page's level (`EXTRA_COLUMNS[level]`) and the limit columns hide when every row's limit is empty (`hiddenLimitColumns`). A SAVED template prints exactly its shown columns — the two rules are the built-in's, not the template's.
- The dialog (`ReportDownloadDialog` `extra`) shows the template lines exactly as the widget dialog does — "Template: <name> (profile)" per section, or "Template: <name> (application-wide)", or "Built-in layout"; a picker when the scope has more than one template; the SUPER_ADMIN link to the editor. The component the widget dialog renders is EXTRACTED (`components/report-template-lines.tsx`) and used by all six dialogs (widget, data report page, trend page ×3 downloads, alarms, audit) — one component, not six copies.

## 9. The builders (web lib)

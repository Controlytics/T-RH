# Rule Chains Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A ThingsBoard-style rule engine: rule chains of typed nodes drawn on a canvas, fed by every system event as a typed message, with per-node debug, the 46 nodes that have a counterpart here (same names, config, relations, semantics), ThingsBoard import/export, and §11 governance.

**Architecture:** One API module `rule-engine` holds the processor (in-memory Main queue, per-originator order), a node registry (one handler file per node; a `RuleContext` with services), a time-boxed `node:vm` for scripts, a durable path through graphile-worker for Delay/Checkpoint, a debug-event writer, and the emit helpers called from the ingest, attribute and alarm code paths. Chains are stored as one document (source of truth) projected into node/connection rows with stable ids. The shared package holds the node catalogue (types, descriptors, zod configs, relations, ThingsBoard class map) and the document schema. The web gets a list page, a canvas editor on `@xyflow/react`, a generic settings-form renderer driven by node descriptors, and a debug panel.

**Tech Stack:** TypeScript; Fastify 5 + Prisma 6 + PostgreSQL 18 + graphile-worker (API); React 19 + SWR + `@xyflow/react` 12.x (web, NEW pure-JS dependency); zod (shared); `node:vm`; `jsonpath-plus` (API, NEW); `mqtt` (already present); vitest (one web file per process; API single fork on `compliance_core_db_test`).

**Spec:** `docs/superpowers/specs/2026-11-03-rule-chains-design.md` (§15 = the controller's calls; §7 = the node catalogue with statuses).

## Global Constraints

- Node names, groups, configuration field names, relation labels and semantics are ThingsBoard's (spec §7); "device" = instrument; `msg` / `metadata` / `msgType` in scripts. Statuses: 46 built, 12 later, 29 none — pinned by a shared test.
- The engine NEVER runs inside an ingest / attribute / alarm transaction and NEVER throws into its caller: emit helpers are called after commit and swallow their own errors into a stat + log (spec G5). A reading is never lost or delayed by the engine.
- Loop guard: writes made by a node carry `metadata.rule_engine_origin = rule_node:<nodeId>`; emit skips rule-node-origin messages unless the chain's `reEnterOnRuleNodeWrites` is true (spec §5, S-2). Save nodes skip ingest-origin messages when `skipSaveNodesForIngestOrigin` (default ON, S-3).
- The chain DOCUMENT is the source of truth; `RuleNode` / `RuleNodeConnection` rows are a projection rebuilt on every save with the document's node ids (D-1). Exactly one root chain (partial unique index). The shipped root chain is ThingsBoard's default (spec §5).
- Scripts: JavaScript in `node:vm` with `timeout = scriptTimeoutMs` (default 2000), `codeGeneration: { strings: false, wasm: false }`, a frozen context exposing only `msg`, `metadata`, `msgType`, `JSON`, `Math`, `Date`, `parseInt`, `parseFloat`, `isNaN`, `isFinite`, `btoa`, `atob`, `String`, `Number`, `Boolean`, `Array`, `Object`. No `require`, `process`, `globalThis`, `fetch`, timers. Documented as a time-box, not a security sandbox.
- Hop limit 200 per message; per-message budget 30 s; Failure on throw with `metadata.error`.
- Durable: Delay and Checkpoint use graphile task `rule_engine_message` (`queueName: rule-engine:<originatorId>`), re-injecting at the node AFTER the delay/checkpoint; a 9th task `rule_engine_debug_sweep` hourly.
- Writes: `RULE_CHAIN_MANAGE` + re-auth `UPDATE_RULE_CHAIN` (Configuration category, ships OFF) + `reason` + audit `RULE_CHAIN_CREATED / UPDATED / DELETED / IMPORTED / ROOT_CHANGED / DEBUG_CLEARED` with the whole document; reads `RULE_CHAIN_READ`; `MANAGE` implies `READ` via `PERMISSION_IMPLIED_BY`.
- A rule-created alarm: `source=RULE`, `metric=CUSTOM` (new enum value, its own migration), `ruleSnapshot = { alarmType, nodeId, chainId, details }`, dedupe by partial unique index `alarms_active_rule_type_unique ON alarms (instrument_id, (rule_snapshot->>'alarmType')) WHERE state='ACTIVE' AND source='RULE'`; its display name = `ruleSnapshot.alarmType`.
- Counts that move (re-derive with the root CLAUDE.md commands): modules 27 → 28; models 40 → 44; enums 13 → 14; permissions 46 → 48; reauth 58 → 59; audit 105 → 111 / 118 → 124; sidebar 15 → 16; tree groups 15 → 16, nodes 56 → 58, privileges 39 → 41; defs 37 → 39; routes 57 → 59; queue tasks 7 → 9; type files 40 → 42 (`rule-nodes.ts`, `rule-chain-document.ts`).
- Tests one web file per process by exit code; API e2e single fork on the test DB; mutation-check each new rule named; tsc ×3, lint, `scripts/verify-migrations.ps1` before hand-over. Commits end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`. The working tree carries untracked `DS/`, `OQ/`, `TCPIP/`, `DS.docx` — never commit them; stage by path.

## Review Focus

1. A burst of 10,000+ readings while a chain has a slow REST node: the Main queue must drop the OLDEST of the largest backlog, count it, and never block ingest — pinned in Task 3 (queue capacity test) and watched in the final review.
2. A chain cycle (Rule chain A → B → A, or a Switch looping to itself) must end at the hop limit with `Failure` and one debug event saying `HOP_LIMIT`, not hang the loop — Task 3.
3. A script that loops forever or throws must end the message on `Failure` within `scriptTimeoutMs` and leave the engine serving other originators — Task 3 (VM) + Task 4 (script nodes).
4. The shipped root chain over live ingest must cost nothing: Save Timeseries on an ingest-origin message is skipped (S-3) and, with the skip OFF, is an upsert no-op that writes no audit row — Task 5 e2e.
5. Import of a real ThingsBoard export must map every known class, mark unknown ones `tb:unsupported` with a warning, and round-trip export → import unchanged — Task 6 with a fixture from ThingsBoard 3.x.

# packages/queue/crontab.txt — Maintenance cron schedules for graphile-worker
# Loaded by the Runner in apps/api/src/app.ts when USE_PG_QUEUE=true.
# Cron format: minute hour day-of-month month day-of-week  task_name  ?key=…
#
# EVERY identifier below MUST have a handler in app.ts's `taskList`.
# graphile-worker does not reject an unknown identifier — it enqueues the job and
# leaves it queued forever, so a handler-less cron entry is an unbounded row leak.
# app.ts already carries a comment describing exactly this failure ("jobs leaked
# into graphile_worker.jobs forever") from when `notification` had no handler —
# but the crontab was never checked for the same class.
#
# REMOVED 2026-07-15 — all three were scheduled for subsystems DELETED in the
# 2026-06-11..17 data-ingestion tear-out, so no handler existed and the jobs
# never completed:
#     * * * * * dlq_check           (DeadLetterQueue model dropped)
#     * * * * * connectivity_check  (ConnectivityStatus model + module dropped)
#     0 2 * * * retention_cleanup   (retention module + retention.def removed)
# The two per-minute entries accrued ~120 rows/hour between them; the queue had
# reached 51,798 orphan jobs when this was found. The `?id=…&max=1` dedup added
# was believed to cap how many were IN FLIGHT at once — it never did (see below),
# and nothing ever completed them, so the table grew without bound.
#
# WHAT THE OPTIONS ACTUALLY MEAN in graphile-worker 0.16.6 (read from
# node_modules/graphile-worker/dist/crontab.js; corrected 2026-10-12 — this block
# used to claim `id` de-duplicated queued jobs and `max` capped queued instances,
# and the alarm evaluator's overlap bug, audit 2026-10-12 #2, hid behind that):
#   - id=…       — the cron item's IDENTIFIER, used only to track its last run
#                  in graphile_worker.known_crontabs (for backfill). It does NOT
#                  de-duplicate jobs and does NOT stop a slow handler overlapping.
#   - max=N      — maxAttempts for the job: how many times a FAILING run is
#                  retried. NOT a concurrency limit, NOT a queue ceiling.
#   - fill=…     — backfill window for runs missed while the process was down.
#   - queue=…    — the named queue. Jobs sharing a queue run ONE AT A TIME; this
#                  is the only option that serialises anything.
#   - jobKey=…   — a pending job with this key is REPLACED by the next tick
#                  (jobKeyMode=replace) instead of a second one being queued.

# Session reaper — every 5 min. Terminates idle/expired sessions + records a
# LOGOUT audit so app-close / window-close / crash logouts are captured.
*/5 * * * * session_sweep ?id=session_sweep&max=1&fill=0s
# Password-expiry notifications — daily 00:00. Warns each user daily for the
# configured window before their password expires + a one-time expiry notice.
# Idempotent (one warning per user per day; expiry notice once per event).
# fill=1d (audit 2026-10-03, DATA-16): a machine that was off at midnight runs
# the missed day's check at the next start instead of skipping that day's
# warnings outright. Bounded to ONE day because the handler is idempotent per
# user per day — replaying a week would still write at most one warning per
# user, but it is the most recent day that carries the expiry notices.
0 0 * * * password_expiry_check ?id=password_expiry_check&max=1&fill=1d
# Telemetry partitions — 1st and 15th at 00:05. Creates next month's partition
# ahead of time. This is a CORRECTNESS entry, not cleanup: Postgres REJECTS an
# insert whose ts falls outside every partition, so if this never runs, device
# telemetry stops being accepted at midnight on the 1st. Twice a month so a
# single missed run (machine off on the 1st) is still covered.
# max=5 (audit 2026-10-12 #11): `max` is maxAttempts, so `max=1` meant a single
# failed run — a DB blip at 00:05 — was never retried. The handler is idempotent
# (CREATE ... IF NOT EXISTS per month), so retrying with graphile's backoff is safe.
5 0 1 * * telemetry_partition_maintenance ?id=telemetry_partition_dom01&max=5&fill=4w
5 0 15 * * telemetry_partition_maintenance ?id=telemetry_partition_dom15&max=5&fill=4w
# Alarm evaluation — every minute. Raises an alarm when a configurable rule's
# condition is met and clears it when the condition ends. Per-minute because an
# excursion nobody is told about for five minutes is five minutes of unrecorded
# deviation. Handler: alarm_evaluation in apps/api/src/app.ts (see the warning at
# the top of this file — an identifier without a handler leaks jobs forever).
# alarm_evaluation is ALSO enqueued on ingest (modules/alarms/enqueue-evaluation.ts),
# which is what makes an excursion raise within ~1s instead of on the next tick.
# THIS ENTRY IS STILL REQUIRED and is not redundant:
#   * OFFLINE alarms fire on the ABSENCE of telemetry. An ingest-triggered
#     evaluation cannot observe an instrument that has gone quiet, because a quiet
#     instrument ingests nothing. This tick is the only thing that can raise one.
#   * It is the safety net when an enqueue fails (that helper never throws, so a
#     queue outage costs promptness, not the reading).
# queue=alarm_evaluation (audit 2026-10-12 #2): the cron pass and the on-ingest
# pass run on ONE serial named queue (ALARM_EVALUATION_QUEUE in src/queues.ts,
# also passed by enqueue-evaluation.ts), so two passes can never overlap. Before
# this, `max=1` was taken for a concurrency limit; it is maxAttempts, and with the
# runner's concurrency of 10 a pass holding a stale reading could clear an alarm a
# parallel pass had just raised.
# jobKey=alarm_evaluation:cron: if the serial queue is busy and a tick is still
# pending, the next tick REPLACES it rather than stacking a second one behind it.
* * * * * alarm_evaluation ?id=alarm_evaluation&max=1&fill=0s&queue=alarm_evaluation&jobKey=alarm_evaluation:cron
